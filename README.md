# Job Agent — персональный помощник для откликов

Job Agent — локальное рабочее пространство, которое помогает пройти путь от исходного PDF-резюме до проверенного отклика на вакансию:

1. импортировать и структурировать резюме;
2. подтвердить факты профиля;
3. разобрать требования вакансии;
4. оценить соответствие кандидата;
5. подготовить доказательное резюме под роль;
6. собрать ATS-friendly PDF;
7. заполнить форму отклика и запросить подтверждение перед отправкой.

Система не считает требование выполненным без ссылки на подтверждённый факт кандидата. AI может выбирать, переставлять и переформулировать подтверждённый материал, но не должен добавлять неподтверждённые утверждения.

> Проект уже реализует основное backend-ядро и локальный интерфейс, но ещё находится на пути к полноценному персональному MVP. Текущие ограничения и план завершения описаны в разделе [План до персонального MVP](#план-до-персонального-mvp).

## Что уже работает

- независимые профили кандидата (`identity`);
- импорт текстовых и сканированных PDF-резюме;
- позиционные текстовые блоки и provenance до страницы и координат источника;
- структурированный разбор резюме и подтверждение найденных элементов;
- канонический профиль с контактами, опытом, навыками и проверенными фактами;
- структурированный анализ вакансии;
- requirement → evidence matrix, score и рекомендация;
- evidence-based tailoring без добавления неподтверждённых фактов;
- выбор контактов, опыта и навыков перед сборкой версии резюме;
- версионированные варианты резюме;
- ATS-friendly PDF с встроенными шрифтами и проверкой текста/layout;
- модель отклика и обязательное подтверждение перед Submit;
- Playwright runner с паузами на CAPTCHA, OTP, авторизацию и ошибки формы;
- возобновляемая browser session, диагностические snapshots и audit trail в PostgreSQL.

## Требования

- Java 21;
- Docker с Docker Compose — для PostgreSQL;
- доступ к OpenAI API — только если нужен полноценный AI-разбор;
- Tesseract — только для PDF без текстового слоя;
- Chromium для Playwright — только для браузерного автозаполнения.

Локальный Gradle устанавливать не нужно: wrapper уже включён в репозиторий.

## Быстрый старт

### 1. Запустить PostgreSQL

```bash
docker compose up -d postgres
```

Контейнер создаёт базу `jobagent` и публикует её на `localhost:5433`. Данные сохраняются в Docker volume `jobagent-postgres` между перезапусками контейнера.

### 2. Запустить приложение без AI

```bash
SPRING_PROFILES_ACTIVE=dev ./gradlew bootRun
```

После запуска откройте <http://localhost:8080/>.

Это минимальный локальный режим без внешнего API:

- резюме разбирается детерминированно и извлекает только известные технологии;
- анализ вакансии использует ограниченный встроенный словарь технологий;
- matching выполняется прозрачной локальной эвристикой;
- tailoring только выбирает и переставляет подтверждённый материал, не переписывая его;
- OCR и браузерное автозаполнение выключены.

Такой режим подходит для разработки и проверки интерфейса, но не даёт полного качества разбора реальных резюме и вакансий.

### 3. Рекомендуемый запуск с OpenAI

```bash
OPENAI_ENABLED=true \
OPENAI_API_KEY='<your-api-key>' \
SPRING_PROFILES_ACTIVE=dev \
./gradlew bootRun
```

При `OPENAI_ENABLED=true` через OpenAI Responses API выполняются:

- декомпозиция PDF-резюме;
- анализ вакансии;
- evidence-based matching;
- адаптация резюме под вакансию.

Все четыре операции используют strict JSON Schema. Перед сохранением сервер проверяет evidence-ссылки, числовые утверждения и принадлежность элементов исходному резюме.

### 4. Добавить OCR для сканированных PDF

Сначала установите Tesseract и языковые пакеты, которые собираетесь использовать. Затем запустите:

```bash
TESSERACT_ENABLED=true \
TESSERACT_LANGUAGES='eng+rus' \
SPRING_PROFILES_ACTIVE=dev \
./gradlew bootRun
```

OCR используется только как fallback, когда в PDF нет пригодного текстового слоя. Если OCR выключен, такой файл вернёт ошибку `RESUME_TEXT_NOT_FOUND`.

### 5. Включить браузерное автозаполнение

Один раз установите Chromium для Playwright:

```bash
./gradlew playwrightInstall
```

Затем явно включите runner и перечислите разрешённые хосты:

```bash
PLAYWRIGHT_ENABLED=true \
PLAYWRIGHT_HEADLESS=false \
PLAYWRIGHT_ALLOWED_HOSTS='boards.greenhouse.io,job-boards.greenhouse.io' \
SPRING_PROFILES_ACTIVE=dev \
./gradlew bootRun
```

`PLAYWRIGHT_ALLOWED_HOSTS` обязателен при включённом Playwright. Значения разделяются запятыми. Разрешается указанный домен и его поддомены; остальные HTTPS-запросы браузера блокируются. Если форма использует отдельные домены для входа, редиректов или обязательных ресурсов, их тоже нужно добавить в список.

Для первой проверки рекомендуется `PLAYWRIGHT_HEADLESS=false`: вы увидите окно браузера и сможете вручную пройти CAPTCHA, OTP или авторизацию.

### Полный пример запуска

```bash
OPENAI_ENABLED=true \
OPENAI_API_KEY='<your-api-key>' \
TESSERACT_ENABLED=true \
TESSERACT_LANGUAGES='eng+rus' \
PLAYWRIGHT_ENABLED=true \
PLAYWRIGHT_HEADLESS=false \
PLAYWRIGHT_ALLOWED_HOSTS='boards.greenhouse.io,job-boards.greenhouse.io' \
SPRING_PROFILES_ACTIVE=dev \
./gradlew bootRun
```

Не включайте OCR или Playwright, если они не нужны: оба режима добавляют внешние runtime-зависимости, а сохранение browser state также влияет на модель приватности.

## Переменные окружения

Ниже перечислены все переменные, которые приложение читает напрямую из `application.yml`.

### PostgreSQL

| Переменная | По умолчанию | Когда задавать | На что влияет |
| --- | --- | --- | --- |
| `DB_URL` | `jdbc:postgresql://localhost:5433/jobagent` | Если PostgreSQL работает не из приложенного Compose или использует другой порт/базу | JDBC URL основной базы данных |
| `DB_USERNAME` | `jobagent` | Если учётная запись БД отличается от Compose-конфигурации | Пользователь PostgreSQL |
| `DB_PASSWORD` | `jobagent` | Если пароль БД отличается от Compose-конфигурации | Пароль PostgreSQL |

Для стандартного локального запуска эти переменные передавать не нужно.

### OpenAI

| Переменная | По умолчанию | Когда задавать | На что влияет |
| --- | --- | --- | --- |
| `OPENAI_ENABLED` | `false` | Установите `true`, чтобы включить AI-разбор | Переключает детерминированные компоненты на OpenAI для resume decomposition, vacancy analysis, matching и tailoring |
| `OPENAI_API_KEY` | пусто | Обязательно при `OPENAI_ENABLED=true` | Bearer token для OpenAI API; без него приложение не запустится в AI-режиме |
| `OPENAI_MODEL` | `gpt-5.6` | Если нужна другая совместимая модель | Модель для всех structured-output запросов |
| `OPENAI_BASE_URL` | `https://api.openai.com` | Только при использовании совместимого proxy или другого API endpoint | Базовый URL; клиент добавляет путь `/v1/responses` |

Если `OPENAI_ENABLED=false`, `OPENAI_API_KEY` не нужен и сетевые запросы к OpenAI не выполняются.

### OCR/Tesseract

| Переменная | По умолчанию | Когда задавать | На что влияет |
| --- | --- | --- | --- |
| `TESSERACT_ENABLED` | `false` | Установите `true` для обработки сканированных PDF | Включает OCR fallback |
| `TESSERACT_COMMAND` | `tesseract` | Если бинарник находится не в `PATH` или имеет другое имя | Команда/путь запуска Tesseract |
| `TESSERACT_LANGUAGES` | `eng+rus` | Подберите под языки резюме и установленные language packs | Значение параметра Tesseract `-l` |
| `TESSERACT_DPI` | `300` | Если нужен компромисс между скоростью и качеством | DPI рендера страниц перед OCR; допустимо `150..600` |
| `TESSERACT_TIMEOUT_SECONDS` | `45` | Для больших или сложных страниц | Максимальное время OCR одной страницы; допустимо `1..300` секунд |

Включение OCR без доступного бинарника приводит к `OCR_UNAVAILABLE`. Отсутствующий language pack обычно приводит к `OCR_FAILED`.

### Browser automation/Playwright

| Переменная | По умолчанию | Когда задавать | На что влияет |
| --- | --- | --- | --- |
| `PLAYWRIGHT_ENABLED` | `false` | Установите `true` для реального браузерного заполнения | Регистрирует Playwright browser runner; без него browser run возвращает `BROWSER_RUNNER_DISABLED` |
| `PLAYWRIGHT_HEADLESS` | `true` | Используйте `false` для отладки, CAPTCHA, OTP и ручной авторизации | Показывает или скрывает окно Chromium |
| `PLAYWRIGHT_ALLOWED_HOSTS` | пусто | Обязательно при `PLAYWRIGHT_ENABLED=true` | Список разрешённых доменов через запятую; действует как защита от перехода на произвольные URL |
| `PLAYWRIGHT_NAVIGATION_TIMEOUT_MS` | `30000` | Если страницы ATS загружаются дольше 30 секунд | Таймаут навигации в миллисекундах; должен быть положительным |
| `PLAYWRIGHT_ACTION_TIMEOUT_MS` | `10000` | Если отдельные controls появляются или реагируют медленно | Таймаут fill/click/select операций в миллисекундах; должен быть положительным |
| `PLAYWRIGHT_PERSIST_STORAGE_STATE` | `false` | Включайте только осознанно, если browser session должна переживать рестарт | Сохраняет cookies и local storage ATS-сессии в PostgreSQL |

`PLAYWRIGHT_PERSIST_STORAGE_STATE=true` может сохранить авторизационные cookies. Используйте эту настройку только на доверенном локальном компьютере и защищайте backup базы данных.

### PDF renderer

| Переменная | По умолчанию | Когда задавать | На что влияет |
| --- | --- | --- | --- |
| `RESUME_MAX_PAGES` | `3` | Если допустим другой максимальный размер CV | PDF длиннее лимита отклоняется с `RESUME_PAGE_LIMIT_EXCEEDED` |

### Spring profile

`SPRING_PROFILES_ACTIVE=dev` включает локальный dev-профиль. В текущем проекте он отключает SQL-логирование и активирует dev seed-конфигурацию приложения. Для обычного локального запуска используйте этот профиль явно, как в примерах выше.

## Основной пользовательский сценарий

### 1. Подготовить профиль

1. Откройте раздел «Профиль кандидата».
2. Выберите существующую identity или создайте новую.
3. Загрузите PDF до 5 МБ и 20 страниц.
4. Проверьте распознанные элементы.
5. Подтвердите только сведения, которые считаете корректными.

Первый подтверждённый импорт создаёт основу профиля. Следующие импорты в режиме `ENRICH` дополняют её, не удаляя уже подтверждённое позиционирование. Исходный PDF, извлечённый текст, позиционные блоки и структурированный snapshot сохраняются в PostgreSQL.

### 2. Добавить и проанализировать вакансию

Вставьте компанию, название роли, локацию, ссылку и полное описание вакансии. Результат содержит:

- структурированные требования;
- score от 0 до 100;
- рекомендацию `PRIORITY`, `APPLY`, `MAYBE` или `REJECT`;
- requirement → evidence matrix;
- отсутствующие требования и hard blockers.

Статус `UNASSESSED` означает, что требование не было надёжно проверено. Он намеренно отличается от `MISSING`.

### 3. Собрать резюме под роль

Перед генерацией можно выбрать контакты, опыт и навыки. Tailor получает только:

- элементы подтверждённого резюме;
- проверенные факты профиля;
- структурированный анализ выбранной вакансии.

Каждый вариант получает собственные `variantId` и `version`; предыдущие версии не изменяются. PDF строится как одноколоночный A4-документ с встроенным Liberation Sans, кликабельными контактами и повторной проверкой извлечённого текста.

### 4. Подготовить отклик

Отклик проходит состояния:

```text
DRAFT → FILLING → NEEDS_INPUT → READY_TO_SUBMIT → SUBMITTED
                                      └──────────→ FAILED
```

Имя и контакты берутся из подтверждённого резюме. Зарплата, sponsorship, relocation, демографические и другие чувствительные ответы никогда не выводятся косвенно: они должны прийти из явных настроек, каталога ответов или решения пользователя.

Финальный Submit требует отдельного approval, связанного с hash текущего резюме, ответов и вложений. Любое изменение после approval делает подтверждение устаревшим.

## Текущие ограничения интерфейса

Backend уже поддерживает больше операций, чем текущий frontend. До завершения персонального MVP важно учитывать:

- нет полноценной воронки откликов после статуса `SUBMITTED`.

Из-за этих ограничений ручные API-вызовы всё ещё могут понадобиться для части approval/browser workflow.

## API: основные точки входа

Все endpoint находятся под `/api/v1`.

| Возможность | Endpoint |
| --- | --- |
| Активный профиль | `GET/PUT /candidate-profile` |
| Identity | `GET/POST /candidate-identities`, `POST /candidate-identities/{id}/activate` |
| Импорт резюме | `POST /candidate-profile/resume-imports` |
| Diff импорта | `GET /candidate-profile/resume-imports/{importId}/diff` |
| Подтверждение импорта | `POST /candidate-profile/resume-imports/{importId}/confirm` |
| Вакансии | `GET/POST /vacancies`, `DELETE /vacancies/{id}` |
| Анализ вакансии | `POST /vacancies/{id}/analyze` |
| Выбор содержимого CV | `GET /vacancies/{id}/resume-selection` |
| Вариант резюме | `POST /vacancies/{id}/resume-variants` |
| PDF | `GET /resume-variants/{variantId}/pdf` |
| Настройки отклика | `GET/PUT /application-settings` |
| Каталог ответов | `GET /application-answers`, `PUT/DELETE /application-answers/{key}` |
| Черновик отклика | `POST /vacancies/{id}/application-drafts` |
| Browser run | `POST /application-drafts/{draftId}/browser-runs` |
| Продолжение browser run | `POST /application-drafts/{draftId}/browser-runs/resume` |
| Browser session/audit | `GET /application-drafts/{draftId}/browser-session`, `/browser-audit`, `/browser-diagnostics` |
| Финальное подтверждение | `POST /application-drafts/{draftId}/submit-approval` |
| Отправка | `POST /application-drafts/{draftId}/submit` |

Ошибки API имеют единый вид:

```json
{
  "code": "VACANCY_NOT_FOUND",
  "message": "Vacancy not found",
  "details": {}
}
```

Stack trace клиенту не возвращается.

## Архитектура и гарантии

Код сгруппирован по возможностям:

- `candidate` — identity, профиль и импорт резюме;
- `vacancy` — вакансии;
- `matching` — анализ и сопоставление;
- `tailoring` — версии резюме под роль;
- `rendering` — генерация и проверка PDF;
- `applying` — ответы, approval workflow и браузерная подача.

Внутри каждой возможности используются слои `domain`, `application`, `infrastructure` и `api`. HTTP и JPA не входят в доменные модели.

Ключевые защитные свойства:

- LLM получает текст вакансий и резюме как недоверенные данные, а не инструкции;
- matcher может ссылаться только на проверенные facts;
- decomposer может ссылаться только на переданные PDF blocks;
- tailor может ссылаться только на подтверждённые resume elements и facts;
- неизвестные evidence ID и неподтверждённые элементы отклоняются;
- новое числовое утверждение без числа в evidence отклоняется;
- browser runner разрешает только HTTPS-хосты из allowlist;
- audit не сохраняет значения ответов и содержимое файлов;
- Submit невозможен без отдельного актуального approval;
- повторные browser actions защищены idempotency key и checkpoint.

## План до персонального MVP

Персональный MVP считается готовым, когда один пользователь может на чистой установке без `curl` и ручного редактирования БД пройти путь:

```text
профиль → вакансия → проверенное tailored CV → заполненная форма
→ финальный review → отправка → сохранённый результат
```

## Критерии готовности MVP

MVP можно считать завершённым, когда выполняются все условия:

- новый пользователь запускает проект по README без знания внутренней архитектуры;
- интерфейс заранее показывает, какие возможности выключены и как их включить;
- реальное резюме можно импортировать, исправить и подтвердить без API;
- пользователь видит и подтверждает все изменения tailored CV;
- отклик можно закончить вручную или через browser runner без `curl`;
- непосредственно перед Submit видны все отправляемые значения и вложения;
- после перезапуска приложения незавершённый отклик можно продолжить;
- отправленный отклик появляется в истории и может получить следующий статус;
- данные можно экспортировать, восстановить и удалить;
- полный happy path покрыт автоматическим тестом и ручным smoke-test на реальной ATS.
